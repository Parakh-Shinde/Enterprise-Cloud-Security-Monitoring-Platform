# Incident Response Runbook

## Purpose

This runbook defines the investigation and response process for security alerts generated by the Enterprise Cloud Security Monitoring Platform.

It provides a repeatable workflow for validating alerts, collecting evidence, assessing impact, recommending containment, documenting decisions, and closing incidents.

> This project is a controlled security lab. Destructive containment actions are not automated. Any blocking, account modification, firewall change, or service disruption requires analyst approval.

---

## Scope

This runbook covers alerts generated from:

- AWS CloudTrail
- AWS WAF
- VPC Flow Logs
- Apache access and error logs
- Linux authentication logs
- Linux system logs
- Splunk Enterprise scheduled detections

The monitored environment includes:

- Two Ubuntu DVWA web servers
- AWS Application Load Balancer
- AWS WAF Web ACL
- Splunk Enterprise SIEM server
- AWS CloudTrail
- CloudWatch Logs
- Amazon S3 and SQS
- VPC Flow Logs

---

## Incident Response Principles

1. Validate the detection before taking action.
2. Preserve the original security evidence.
3. Determine the affected identity, host, application, and AWS resource.
4. Distinguish authorized testing from unauthorized activity.
5. Use the least disruptive containment action.
6. Require analyst approval for any production-impacting action.
7. Record all decisions, timestamps, evidence, and actions.
8. Tune detections after completing the investigation.

---

## Severity Classification

| Severity | Description | Example | Target response |
|---|---|---|---:|
| Critical | Confirmed activity that could cause account compromise, security-control failure, or major exposure | CloudTrail disabled, successful privilege escalation, confirmed compromised administrator | Immediate |
| High | Strong evidence of malicious activity affecting an important resource | SSH brute force, SQL injection, successful login after repeated failures | Within 30 minutes |
| Medium | Suspicious activity requiring investigation but without confirmed impact | Reconnaissance, repeated WAF matches, abnormal API calls | Within 4 hours |
| Low | Low-confidence or informational event | Isolated failed request or expected scanner activity | Within 1 business day |

These response targets are lab objectives and not contractual service-level agreements.

---

## Roles and Responsibilities

| Role | Responsibility |
|---|---|
| SOC analyst | Validate alerts, collect evidence, determine severity, and document findings |
| Cloud security engineer | Investigate AWS resources, IAM activity, logging controls, and network configuration |
| System administrator | Assist with host isolation, account review, patching, and service restoration |
| Incident owner | Coordinate response activities and approve incident closure |
| Change approver | Approve containment actions that could affect availability or access |

In this lab, one person may perform several roles, but each decision should still be documented.

---

## Investigation Workflow

| Phase | Analyst activity | Expected output |
|---|---|---|
| 1. Alert intake | Review detection name, time, severity, source, and affected asset | Initial alert record |
| 2. Validation | Confirm the event exists in the original log source | True positive, false positive, or inconclusive |
| 3. Scoping | Identify related users, IP addresses, hosts, resources, and events | Incident scope |
| 4. Enrichment | Review CloudTrail, WAF, web, Linux, and network context | Enriched timeline |
| 5. Impact assessment | Determine whether access, data, configuration, or availability was affected | Impact statement |
| 6. Containment decision | Recommend the least disruptive response and obtain approval | Approved response plan |
| 7. Recovery | Restore normal operations and verify security controls | Recovery evidence |
| 8. Closure | Document findings, residual risk, and lessons learned | Completed incident record |
| 9. Detection tuning | Improve thresholds, exclusions, fields, or correlation logic | Updated detection |

---

## Initial Triage Checklist

For every alert, record:

- Detection ID and detection name
- Alert generation time
- Event time and ingestion time
- Severity and confidence
- Source IP and destination IP
- Affected host, user, AWS account, or resource
- AWS Region
- Relevant event name or HTTP request
- Detection rule version
- Related events before and after the alert
- Whether the activity was part of authorized testing
- Analyst name and investigation start time

---

## Evidence Preservation

Before containment:

1. Export the relevant Splunk search results.
2. Preserve the original `_raw` event.
3. Record the search query and time range.
4. Record relevant AWS resource identifiers.
5. Save screenshots of important results.
6. Record CloudTrail `eventID` and `requestID` when available.
7. Record the WAF rule group and matched rule.
8. Preserve timestamps in UTC whenever possible.
9. Avoid modifying the original evidence.

Recommended evidence location:

```text
screenshots/incidents/<incident-id>/
```

Recommended incident identifier:

```text
INC-YYYYMMDD-###
```

# Detection Response Playbooks

## DET-001 — SSH Brute Force

### Validation

- Confirm repeated `Invalid user` or `Failed password` events.
- Extract the source IP.
- Identify all targeted hosts and usernames.
- Check whether any successful authentication followed the failures.

### Investigation

- Review `linux_secure` events from the same IP.
- Search Apache and WAF logs for activity from the same source.
- Check VPC Flow Logs when network ingestion is enabled.
- Identify whether the IP belongs to an authorized testing system.

### Recommended response

- Block the source IP only after validation and approval.
- Restrict SSH access to trusted administrative CIDRs.
- Disable password authentication where operationally possible.
- Review authorized SSH keys.
- Rotate credentials if compromise is suspected.

### Closure condition

Close only after confirming that no unauthorized login occurred or after the affected account and host have been secured.

---

## DET-002 — SQL Injection Attempt

### Validation

- Review the decoded request URI.
- Confirm SQL-related operators, comments, encoded payloads, or known injection patterns.
- Determine the HTTP response code.
- Check whether AWS WAF generated a related match.

### Investigation

- Review all requests from the same source IP.
- Examine Apache error logs for database or application errors.
- Identify the targeted DVWA page and backend server.
- Determine whether the request reached the application.
- Review database and application behavior for signs of successful exploitation.

### Recommended response

- Block the source temporarily if the activity is unauthorized.
- Change the relevant WAF rule from count to block only after testing.
- Correct vulnerable application logic.
- Use parameterized queries and input validation.
- Preserve the request as evidence.

---

## DET-003 — Cross-Site Scripting Attempt

### Validation

- Decode the request.
- Confirm script tags, event handlers, JavaScript schemes, or encoded XSS payloads.
- Determine whether the payload was reflected by the application.

### Investigation

- Review related requests from the source.
- Identify affected parameters and pages.
- Check AWS WAF rule matches.
- Determine whether the activity was authorized DVWA testing.

### Recommended response

- Apply output encoding and input validation.
- Consider enabling the relevant WAF rule in block mode.
- Review session and authentication logs if exploitation succeeded.
- Add a Content Security Policy where appropriate.

---

## DET-004 — Potential IAM Privilege Escalation

### Validation

Review CloudTrail for sensitive actions such as:

- `PutUserPolicy`
- `PutRolePolicy`
- `AttachUserPolicy`
- `AttachRolePolicy`
- `CreateAccessKey`
- `UpdateAssumeRolePolicy`
- `AddUserToGroup`
- `PassRole`

### Investigation

- Identify the actor and session issuer.
- Review the source IP, user agent, Region, and MFA context.
- Compare the activity with approved administrative changes.
- Review subsequent actions performed using the modified permissions.
- Determine whether the actor created persistence.

### Recommended response

- Revoke unauthorized sessions and access keys.
- Remove unauthorized policies or role relationships.
- Preserve the original CloudTrail events.
- Review the affected identity’s recent activity.
- Require MFA and least-privilege access.

---

## DET-005 — CloudTrail Logging Modified or Disabled

### Validation

Review CloudTrail for:

- `StopLogging`
- `DeleteTrail`
- `UpdateTrail`
- `PutEventSelectors`
- `DeleteEventDataStore`

### Investigation

- Identify the actor and authentication method.
- Determine how long logging was affected.
- Check for activity immediately before and after the change.
- Review other Regions and available AWS logging sources.
- Confirm whether the change was authorized.

### Recommended response

- Restore logging immediately after approval.
- Protect the trail and log bucket with restrictive policies.
- Alert on future logging changes.
- Review the account for activity during the visibility gap.

> Validation in this project used non-persistent synthetic logic. CloudTrail was not intentionally disabled.

---

## DET-006 — Security Group Opened to the Internet

### Validation

Review CloudTrail changes that authorize:

```text
0.0.0.0/0
```

or:

```text
::/0
```

to sensitive ports such as SSH, RDP, databases, or Splunk management interfaces.

### Investigation

- Identify the security group and affected resources.
- Review the exposed port range.
- Identify the actor who made the change.
- Determine the duration of exposure.
- Review VPC Flow Logs and host logs for connections during that period.

### Recommended response

- Remove unsafe ingress after approval.
- Restrict access to trusted CIDR ranges.
- Use AWS Systems Manager Session Manager where possible.
- Review exposed systems for suspicious authentication attempts.

---

## DET-007 — Repeated AWS WAF Rule Matches

### Validation

- Identify the client IP.
- Review the matched rule and rule group.
- Determine whether the WAF action was `COUNT`, `ALLOW`, or `BLOCK`.
- Review the number and frequency of matches.

### Investigation

- Correlate the source with Apache access logs.
- Identify targeted URIs and parameters.
- Check for SQL injection, XSS, traversal, or reconnaissance activity.
- Determine whether the source belongs to an authorized test system.

### Recommended response

- Monitor low-confidence matches.
- Rate-limit persistent sources.
- Move validated high-confidence managed rules from count to block mode.
- Add exclusions only when supported by documented false-positive evidence.

---

## DET-008 — Directory Traversal Attempt

### Validation

Look for:

- `../`
- Encoded traversal sequences
- Attempts to access `/etc/passwd`
- Application or configuration files outside the web root

### Investigation

- Decode the request path.
- Review the response code and response size.
- Check Apache errors.
- Determine whether any sensitive file was returned.
- Review other activity from the same source.

### Recommended response

- Block unauthorized sources.
- Normalize and validate file paths.
- Restrict application file permissions.
- Prevent user-controlled input from directly selecting filesystem paths.

---

## DET-009 — Web Reconnaissance and Enumeration

### Validation

- Confirm requests to multiple commonly enumerated paths.
- Identify the number of distinct URIs.
- Review the request rate and user agent.
- Distinguish scanners from normal browsing.

### Investigation

- Identify whether reconnaissance was followed by exploitation attempts.
- Correlate with WAF and Apache errors.
- Review the targeted hosts and applications.
- Compare the IP with authorized testing sources.

### Recommended response

- Monitor or rate-limit the source.
- Block persistent unauthorized scanners.
- Remove unnecessary files, endpoints, and directory listings.
- Avoid exposing application version information.

---

## DET-010 — Successful SSH Login Following Multiple Failures

### Validation

- Confirm multiple failures and a later successful login.
- Verify that events belong to the same source IP and host.
- Identify the authenticated user and authentication method.

### Investigation

- Review commands, processes, and session activity after login.
- Check for privilege escalation or persistence.
- Review file modifications and outbound connections.
- Confirm whether the login was an authorized analyst test.

### Recommended response

- Terminate unauthorized sessions.
- Revoke affected keys or credentials.
- Isolate the host if compromise is confirmed.
- Review `sudo`, process, and network activity.
- Rebuild the host if system integrity cannot be trusted.

---

## False-Positive Handling

An alert may be classified as a false positive only when supporting evidence exists.

Record:

- Why the activity is legitimate
- Owner of the activity
- Source IP or identity
- Approved change or test reference
- Detection condition that caused the alert
- Recommended tuning
- Expiration date for any exception

Do not permanently exclude an IP, user, or resource without review.

---

## Containment Approval

The following actions require explicit approval:

- Blocking an IP address
- Modifying AWS WAF rules
- Changing security groups
- Disabling an IAM user
- Revoking access keys
- Terminating active sessions
- Stopping or isolating an EC2 instance
- Deleting or modifying cloud resources
- Changing production logging configuration

Containment recommendations should include:

- Expected security benefit
- Availability risk
- Affected resources
- Rollback procedure
- Approver
- Execution time
- Validation result

---

## Recovery Validation

After remediation, confirm:

- Required services are operational.
- CloudTrail is actively logging.
- Splunk is receiving current events.
- WAF logging is active.
- Web servers are healthy behind the ALB.
- Unauthorized credentials and permissions are removed.
- Security-group rules match the approved design.
- No related alerts continue to fire unexpectedly.

---

## Incident Closure Criteria

An incident may be closed when:

- The alert has been validated.
- Root cause is known or documented as inconclusive.
- Affected assets and identities have been identified.
- Containment and recovery are complete.
- Evidence has been preserved.
- Residual risk has been accepted or assigned.
- Detection tuning recommendations are documented.
- The incident owner approves closure.

## Operational Limitations

- This environment is a single-node lab SIEM and not a production Splunk cluster.
- VPC Flow Log ingestion may be paused to control event volume and cost.
- AWS WAF may operate in count mode during detection validation.
- DVWA is intentionally vulnerable and must not host real data.
- GuardDuty and AI-assisted analysis are outside the current implemented scope.
- Response actions remain analyst-controlled and are not automatically executed.
